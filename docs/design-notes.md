# 설계 노트 — 왜 이렇게 만들었는가

평가항목 2·3·4는 "설명할 수 있는가"를 묻습니다. 구현 근거를 여기에 정리합니다.

---

## Ⅰ. 구조 설계

### Q1. Git 수집 로직과 AI API 호출 로직을 왜 분리했나?

**두 작업의 성질이 정반대이기 때문입니다.**

| | `gitctx.py` (수집) | `ai_client.py` (호출) |
|---|---|---|
| 위치 | 로컬 | 원격 |
| 결과 | 결정적 (같은 입력 → 같은 출력) | 확률적 |
| 비용 | 무료 | 유료 (토큰 차감) |
| 실패 원인 | git 미설치, 저장소 아님 | 인증, 네트워크, 한도 초과 |
| 재시도 | 의미 없음 (또 실패함) | 의미 있음 (일시적 장애일 수 있음) |

**분리하지 않으면 잃는 것 세 가지**

1. **실패 지점 구분 불가.** 한 함수에서 diff도 뜨고 API도 부르면, 예외가 났을 때 "git이 실패했나 API가 실패했나"를 사용자에게 알려줄 수 없습니다. 실제로 이 도구의 오류 메시지는 `[ERROR] Git 저장소가 아닙니다`와 `[ERROR] AI API 오류 [HTTP 401]`로 완전히 다른 조치를 안내합니다.
2. **단독 테스트 불가.** 지금은 API 키 없이도 `gitctx.build_context()`만 돌려 수집 로직을 검증할 수 있습니다. `--dry-run` 옵션이 존재할 수 있는 것도 이 분리 덕입니다.
3. **재시도 정책 혼선.** API 호출은 재시도할 수 있지만 git 수집은 재시도해도 같은 결과입니다. 섞이면 "재시도"라는 말의 의미가 모호해집니다.

### Q2. 프롬프트 구성과 출력 포맷팅을 어떻게 분리했고, 왜?

**"부탁"과 "강제"는 보장 수준이 다르기 때문입니다.**

| 계층 | 파일 | 성격 | 보장 |
|---|---|---|---|
| 프롬프트 | `prompts.py` | AI에게 부탁 | **없음** — 확률적 |
| 검증·후처리 | `formatter.py` | 코드가 강제 | **있음** — 결정적 |

`SYSTEM_COMMIT`에 "제목은 50자 이내로 씁니다"라고 써도, 같은 프롬프트로 100번 호출하면 몇 번은 어깁니다. `temperature=0.0`으로 낮춰도 0이 되지 않습니다. 반면 `formatter.truncate_at_word(title, 72)`는 100% 보장입니다.

**분리하지 않으면**: "왜 가끔 72자를 넘지?"를 만났을 때 프롬프트를 고쳐야 할지 후처리를 고쳐야 할지 판단할 지점 자체가 없습니다.

**둘 사이의 계약**: `prompts.py`가 출력 형식(`<<<TITLE>>>` / `<<<BODY>>>`, `## Why` 헤더)을 정의하고 `formatter.py`가 그 형식을 파싱합니다. 계약이라 한쪽만 바꾸면 깨지며, 이 사실을 두 파일의 docstring에 명시했습니다.

### Q3. API 파라미터를 왜 CLI 옵션으로 설계했나?

**재현성과 실험 통제 때문입니다.**

- **재현성**: `--temperature 0.0`으로 고정하면 같은 diff에서 같은 결과가 나오는지 확인할 수 있습니다. 하드코딩되어 있으면 "왜 어제와 다른 결과가 나오지?"를 추적할 수 없습니다.
- **실험 통제**: 프롬프트를 고쳐가며 품질을 개선할 때, 파라미터가 고정되어 있어야 **프롬프트 변경의 효과만 분리해서** 관찰할 수 있습니다. 파라미터를 바꾸려고 매번 코드를 고치면 "코드가 달라져서 출력이 달라진 건지 파라미터 때문인지" 통제 변수가 무너집니다.
- **용도별 최적값이 다름**: 커밋 메시지(짧고 형식적)와 PR 본문(길고 서술적)은 적정 `max_tokens`가 다릅니다. 그래서 서브커맨드별 기본값을 각각 700 / 1200으로 두고, 옵션으로 덮어쓸 수 있게 했습니다.

### Q4. 오류 처리를 어떤 방식으로 구현했고, 왜?

**원칙: 모든 오류 메시지는 "무엇이" 실패했고 "왜"인지, 그리고 "무엇을 하면 되는지"를 담는다.**

```python
raise AIError(f"AI API 오류 [HTTP {code}] {guide}\n       서버 응답: {detail}")
```

- **키 미설정은 가장 먼저 검사합니다.** git을 다 수집한 뒤에 "키가 없다"고 하면 사용자의 시간을 낭비시킵니다. `run()` 첫 줄이 `load_api_key()`인 이유입니다.
- **예외를 계층별로 나눴습니다.** `GitError` / `AIError`(하위: `MissingAPIKeyError`, `CallBudgetExceeded`) / `ValueError`(파라미터). `main()`에서 한 번에 잡되 메시지는 각자 갖습니다.
- **HTTP 상태 코드를 원인별로 매핑했습니다.** 게이트웨이는 원래 API에 없던 실패 모드를 만듭니다. `403 Provider credentials are unavailable`은 **내 키는 멀쩡한데 기관의 provider 키가 없는** 경우라, "키를 확인하세요"가 아니라 "운영자에게 문의하세요"가 맞는 안내입니다.
- **파라미터는 요청 전에 검증합니다.** `temperature=2.0`은 서버가 400을 주지만, 그러면 네트워크 왕복 한 번을 낭비합니다. `validate_temperature()`로 미리 막습니다.
- **exit code를 구분합니다.** 정상 0 / 변경 없음 0 / 오류 1 / 중단 130. **변경 없음은 오류가 아닙니다** — 사용자가 잘못한 게 없으므로 0입니다.

## Ⅱ. AI 파라미터와 프롬프트

### Q5. `temperature`를 높이거나 낮추면 결과가 어떻게 달라지나?

`temperature`는 다음 토큰의 **확률분포를 얼마나 평탄하게 만들지**를 조절합니다.

| 값 | 동작 | 결과 |
|---|---|---|
| 0.0 | 항상 최고 확률 토큰 선택 | 결정적, 재현 가능, 보수적, 반복적 표현 |
| 0.2 (기본) | 거의 결정적 | 형식이 안정적이면서 문장은 자연스러움 |
| 0.7~1.0 | 낮은 확률 토큰도 선택 | 다양하고 창의적, 형식 위반 확률 증가 |

**기본값을 0.2로 둔 이유**: 커밋 메시지는 "창의적인 글"이 아니라 **형식이 정해진 요약**입니다. 다양성이 필요 없고, 오히려 같은 변경에 대해 매번 다른 요약이 나오면 신뢰하기 어렵습니다.

> ⚠️ **Anthropic 규격의 범위는 0.0~1.0**입니다. OpenAI(0.0~2.0)와 다르며, 2.0을 보내면 400이 납니다. 그래서 CLI에서 미리 검증합니다.

### Q6. `max_tokens`는 결과물에 어떤 영향을 미치며, 어떤 기준으로 값을 정했나?

**핵심: `max_tokens`는 길이 조절기가 아니라 천장입니다.**

자연 출력보다 높으면 **아무 일도 하지 않고**, 낮으면 문장 중간에서 끊습니다. 그 사이는 없습니다.

| max_tokens | 실제 출력 | `stop_reason` |
|---:|---:|---|
| 300 | 68 | `end_turn` (상한이 놀고 있음) |
| 100 | 68 | `end_turn` (상한이 놀고 있음) |
| 60 | 60 | `max_tokens` (끊김) |

300을 주든 100을 주든 68토큰입니다 — **모델은 상한에 맞춰 스스로 줄이지 않습니다.**
품질과의 관계는 비대칭입니다: 낮게 잡아 망가뜨릴 수는 있어도 넉넉히 잡아 좋아지지는 않습니다.

가장 위험한 점: **잘려도 HTTP 200으로 돌아옵니다.** 에러가 아니라 정상 응답이고, `stop_reason: "max_tokens"`를 확인해야만 알 수 있습니다. PR 본문에서 이게 일어나면 마지막 `## How to Test` 섹션이 통째로 사라진 채 "성공"으로 처리됩니다.

```python
@property
def was_truncated(self) -> bool:
    return self.stop_reason == "max_tokens"
```

**값을 정한 기준**

| 명령 | 기본값 | 근거 |
|---|---|---|
| `commit` | 700 | 제목 1줄 + 불릿 3~5개면 200~300 토큰. 여유 2배 |
| `pr` | 1200 | 3개 섹션 × 불릿 2~4개 → 500~700 토큰. 여유 2배 |

**"짧게 써라"는 프롬프트로 지시하고, `max_tokens`는 사고 방지용 상한으로 넉넉히 잡는 것**이 정석입니다. 길이 통제를 `max_tokens`로 하면 문장이 중간에 끊깁니다.

### Q7. 프롬프트에 어떤 정보를 포함했고, 왜 그렇게 구성했나?

`prompts._context_block()`이 **요약 → 상세** 순서로 재료를 쌓습니다.

| 넣은 것 | 이유 |
|---|---|
| 현재 브랜치 | PR 초안에 필요. 브랜치명 자체가 의도를 담고 있는 경우가 많음 |
| 변경 규모 (파일 수, +/- 줄 수) | 규모에 맞는 서술 톤을 잡게 함 |
| **변경된 파일 목록 (상태 포함)** | diff보다 **먼저** 배치. 전체 그림을 준 뒤 헌크를 읽게 하면 맥락을 갖고 읽음 |
| 최초 커밋 여부 | 없으면 존재하지 않는 이전 상태와의 비교를 지어냄(환각) |
| 마스킹·절단 사실 | 모르면 `[MASKED_API_KEY]`라는 자리표시자 자체를 변경 내용으로 서술함 |
| sanitize된 diff | 실제 재료. ` ```diff ` 펜스로 감싸 경계를 명확히 함 |
| 출력 형식 지시 | `formatter`가 파싱할 계약 |

**원칙: 모델이 diff만 봐서는 알 수 없는 맥락만 명시적으로 넣는다.** diff에서 읽어낼 수 있는 것(어떤 함수가 바뀌었는지 등)은 굳이 요약해 넣지 않습니다 — 토큰만 쓰고 정보는 중복입니다.

### Q7-b. 출력 언어와 커밋 컨벤션은 어떤 근거로 정했나?

**명세를 먼저 확인했습니다.**

| 확인 지점 | 결과 |
|---|---|
| 본문에 "한국어/영어/언어" 언급 | 0건 |
| 평가 메타 `evLang` / `language` | 둘 다 `null` |
| 결과 예시(8절)의 실제 문구 | 전부 한국어 + `feat:` 접두사 |
| 8절 첫 문장 | "정답이 아니라 참고 예시다. 실제 문구는 얼마든지 달라도 된다." |

**결론: 언어는 자유이지만, 명세 예시에 맞춰 한국어 + `feat:` 접두사로 고정했습니다.**

**왜 "명시"가 중요한가**: 지시하지 않았을 때 실제로 커밋은 영어, PR 본문은 한국어로
갈렸습니다. 모델은 빈칸을 맥락으로 채우는데 맥락은 입력마다 다르므로,
**명시하지 않은 것은 "알아서 잘"이 아니라 "매번 다르게"가 됩니다.**

**단, 섹션 헤더 `## Why` / `## What` / `## How to Test`는 영어가 강제**입니다
(기능 요구사항 4번에 명시). 프롬프트에 "이 헤더만은 번역하지 말라"고 따로 적었습니다.

**컨벤션을 마스킹처럼 규칙표로 만들지 않은 이유**: 성질이 다릅니다.

| | 마스킹 | 커밋 컨벤션 |
|---|---|---|
| 성격 | 보안 경계 | 내용 품질 |
| 어겼을 때 | 비밀 유출 — 되돌릴 수 없음 | 읽기 불편 — 사람이 고치면 됨 |
| 구현 | `sanitizer.py`에서 **코드로 강제** | `prompts.py`에서 **프롬프트로 부탁** |
| 명세 | 제약사항에 명시 | 결과 예시에만 등장 |

다만 프롬프트로 부탁한 것이 지켜졌는지 확인하려고 `formatter`에 접두사 검사를
**WARN 수준으로** 넣었습니다. ERROR가 아니므로 재생성을 트리거하지 않고,
접두사가 없어도 출력은 유효합니다.

### Q8. 길이/형식 규칙을 "재생성"과 "후처리" 중 무엇으로 해결했나?

**둘 다 씁니다. 위반을 두 종류로 나눠 각각에 맞는 방법을 쓰는 하이브리드입니다.**

| 유형 | 예 | 성질 | 해결 |
|---|---|---|---|
| **양적 위반** | 제목 80자, 마크다운 펜스, 따옴표 | 정답이 **유일하게 결정됨** | **후처리** |
| **구조적 위반** | `## How to Test` 섹션 자체가 없음 | **정보 부족** | **재생성** |

```python
issues = validate(result)
if not issues:
    return result
if has_structural_failure(issues):        # 섹션 누락 등
    result = client.complete(..., retry_hint)   # 2회차
return postprocess(result)                # 나머지는 코드로 절단
```

**왜 전부 후처리가 아닌가**: 없는 섹션에 헤더를 만들어 넣을 수는 있지만 **내용이 없습니다.** 빈 스텁이 들어갈 뿐입니다. 이건 형식 문제가 아니라 정보 부족이므로 코드로 만들 수 없습니다.

**왜 전부 재생성이 아닌가**: 제목이 80자인 건 자르면 정답입니다. 재생성하면 토큰을 또 쓰고 결과는 같거나 더 나쁩니다. 또한 재생성은 **성공 보장이 없습니다** — 두 번째도 어길 수 있습니다.

**재시도 예산**: 최대 1회(총 2회 상한, `MAX_CALLS_PER_RUN = 2`)입니다. 과제 제약 "1회 실행 시 호출 1~2회"가 곧 이 예산의 근거입니다. 확률적 시스템에서 재시도는 **반드시 상한과, 상한 도달 시의 결정적 fallback이 함께** 설계돼야 합니다. 그래서 재생성에도 실패하면 후처리로 착지하고, 무엇이 비었는지 `[WARN]`으로 알립니다.

## Ⅲ. 운영 관점

### Q9. AI가 생성한 텍스트를 바로 쓰지 않고 검토해야 하는 이유는?

1. **AI는 diff에 없는 내용을 지어낼 수 있습니다(환각).** 특히 변경 *이유*는 diff에 안 적혀 있습니다. 코드는 "무엇을 바꿨는지"만 담고 "왜"는 개발자 머릿속에 있으므로, AI가 쓰는 `## Why`는 **추측**입니다.
2. **safe-mode 절단으로 일부만 보고 판단했을 수 있습니다.** 200줄 상한을 넘긴 변경은 AI가 보지 못한 부분이 있습니다.
3. **커밋 메시지는 영구 기록입니다.** 히스토리에 남아 나중에 `git log`·`git blame`·릴리스 노트의 근거가 됩니다. 틀린 요약은 계속 오해를 만듭니다.
4. **팀 컨벤션은 코드 밖에 있습니다.** 티켓 번호 규칙, 스코프 표기 등은 diff에 없어서 AI가 알 수 없습니다.
5. **책임 소재**: 커밋과 PR은 작성자 이름으로 남습니다. 검토 없이 올리면 AI가 아니라 작성자가 책임집니다.

그래서 이 도구는 **초안 출력까지만** 하고 `git commit`을 실행하지 않으며, 매 실행 끝에 검토 안내를 출력합니다.

### Q10. `git diff`에 민감정보가 포함될 수 있는 상황과 방지 방안은?

**포함될 수 있는 상황**

- `.env`, `config.json` 등 설정 파일을 실수로 추적 중일 때
- 디버깅하다 코드에 키를 임시로 하드코딩했을 때
- 테스트 픽스처·시드 데이터에 실제 이메일·전화번호·주민번호 형식 문자열이 있을 때
- 로그 파일이나 DB 덤프를 커밋할 때
- 주석에 내부 서버 주소·계정 정보를 적어둔 경우

**방지 방안 (이 도구가 구현한 것)**

| 계층 | 방법 |
|---|---|
| 마스킹 | `MASK_RULES` 13종 정규식으로 패턴 치환 후 전송 (`--no-safe-mode`로만 해제) |
| 전송량 제한 | 최대 10파일 / 200줄 — 노출면과 비용을 함께 줄임 |
| 단일 관문 | 상위 계층은 원본 diff를 만지지 않고 `sanitize()` 결과만 사용 |
| 투명성 | 무엇을 가렸는지 `[INFO]`로 사용자에게, 그리고 AI에게도 알림 |
| 사전 차단 | `.gitignore`에 `.env` 선반영 + `.env.example`만 커밋 |

**관문이 하나여야 하는 이유**: 마스킹 함수가 여러 개면 "어떤 경로로도 원본이 새지 않는다"를 반증할 수 없습니다. 보안 코드는 우회 경로가 0개임을 **코드 구조로** 보여야 합니다.

**규칙 설계 기준** (명세에 구체적 목록이 없어 자체 판단)

1. **구조가 뚜렷해 오탐이 낮은 것부터.** 발급 기관이 정한 접두사(`sk-`, `AKIA`, `ghp_`, `AIza`,
   `xox*`)와 JWT는 우연히 일치할 일이 거의 없습니다. 반대로 "비밀번호처럼 생긴 문자열"을
   잡으려 하면 코드 전체가 마스킹됩니다.
2. **치환문자열에 종류를 남긴다.** `[MASKED]`가 아니라 `[MASKED_EMAIL]`로 쓰면 AI가
   "이메일 관련 변경"임을 알 수 있습니다. **가리는 것은 값이지 맥락이 아닙니다.**
3. **키=값에서는 값만** 가리고 키 이름은 남깁니다.
4. **구체적 규칙을 일반 규칙보다 앞에.** 이미 마스킹된 값은 lookahead로 건너뜁니다.

**오탐을 가르는 세 구분선** — 14개 케이스로 검증했습니다(`docs/verification.md` §8).

| 구분선 | 가르는 것 |
|---|---|
| 값에 **따옴표 필수** | `PASSWORD = "hunter2"`(비밀) vs `password = user.password`(코드) |
| 값 **8자 이상** | `TOKEN_TYPE = "Bearer"`(6자), `MODE = "test"`(4자) 제외 |
| `.env` 규칙은 **`=` 앞뒤 공백 금지** | `.env`는 `KEY=value`, 파이썬은 `key = value` |

세 번째가 특히 중요합니다. 공백 한 글자 차이가 **설정 파일과 코드**를 가릅니다.
이걸 안 걸면 `access_token = response.json()["access_token"]` 같은 평범한 코드가
마스킹되어 diff가 읽을 수 없게 됩니다.

**한계도 인정해야 합니다.** 정규식 마스킹은 알려진 패턴만 잡습니다. 형식이 없는 비밀(내부 URL, 사람 이름, 비즈니스 로직)은 못 잡습니다. 그래서 마스킹은 **최후 방어선이 아니라 안전망**이고, 근본 대책은 애초에 비밀을 커밋하지 않는 것입니다.

### Q11. 팀 프로젝트에 적용한다면 무엇을 먼저 추가하겠는가?

> 이 답은 정답이 없습니다. 아래는 우선순위 **근거를 세우는 방식**의 예시이니, 본인 생각으로 바꿔 답하세요.

우선순위 기준을 **"안 하면 도구를 못 쓰게 되는 것 → 있으면 훨씬 좋아지는 것"** 순으로 잡습니다.

**1순위 — 팀 컨벤션 설정 파일 (`.ai-gitgen.yml`)**
팀마다 커밋 규칙이 다릅니다(prefix, 스코프, 티켓 번호, 언어). 지금은 컨벤션을 바꾸려면 `prompts.py`를 고쳐야 하는데, 그러면 팀원마다 코드가 갈라집니다. 설정을 저장소에 커밋하면 **팀 전체가 같은 규칙**을 쓰고 코드는 공유됩니다. → *도구가 팀 단위로 쓰이려면 반드시 필요*

**2순위 — 브랜치명·이슈 트래커 연동**
`## Why`가 지금은 AI의 추측입니다. 브랜치명(`feature/PROJ-123-...`)에서 티켓을 뽑아 제목/설명을 프롬프트에 넣으면 **추측이 사실로 바뀝니다.** → *결과물 품질에 가장 큰 영향*

**3순위 — diff 요약 압축 (대형 변경 대응)**
현재는 200줄에서 자릅니다. 큰 PR에서는 잘린 부분이 핵심일 수 있습니다. 파일별로 1차 요약 후 종합하면 전체를 보면서도 토큰을 아낄 수 있습니다. → *다만 API 호출이 늘어 비용 제약과 충돌하므로 3순위*

**4순위 — `--apply` 옵션 (git commit 실행)**
편하지만 지금도 복사-붙여넣기로 가능하고, 검토 없이 커밋하는 습관을 만들 위험이 있어 마지막입니다. → *편의는 크지만 리스크가 있어 후순위*
