# 항목 1 — 기능 재현 (7)

## 1-1. 프로젝트 루트에서 커밋 메시지 생성 명령 실행 시 커밋 메시지가 터미널에 출력되는가?

> **한 줄 답** — `python main.py commit` 한 줄이면 `--- Commit Message ---` 구획 안에 제목과 불릿 본문이 출력됩니다.

```bash
python main.py commit
```

```
[INFO] 현재 브랜치: main
[INFO] Git status 수집 완료: 12개 파일 변경 감지
         - 미추적: main.py
         ...
[DONE] 커밋 메시지 생성 완료

--- Commit Message -----------------------------------------
feat: AI 기반 Git 커밋/PR 초안 생성 CLI 도구 초기 구현

- gitctx.py: git status/diff 수집 및 파일 범위 제어 기능 추가
...
------------------------------------------------------------
[INFO] AI API 호출 횟수: 1회 | 사용량: 입력 3826 + 출력 200 토큰 (차감배수 0.5배)
```

변경된 **파일 목록도 함께 출력**됩니다. `git status --porcelain -uall`을 쓰는데,
기본값(`-unormal`)은 `docs/`처럼 디렉터리로 뭉뚱그려 보고해 목록이 부정확해지기 때문입니다.

## 1-2. PR 생성 명령 실행 시 PR 제목과 본문 초안이 터미널에 출력되는가?

> **한 줄 답** — `python main.py pr`로 제목과 본문이 각각 별도 구획으로 출력됩니다.

```bash
python main.py pr
```

`--- PR Title ---`과 `--- PR Body ---` 두 블록으로 나뉘어 출력되므로 복사해서 바로 쓸 수 있습니다.

## 1-3. AI API Key가 설정되지 않은 상태에서 실행하면 오류 메시지가 출력되고 종료되는가?

> **한 줄 답** — 종료 코드 1로 즉시 종료하며, 해결 방법(`export` 예시와 키 발급 URL)까지 함께 안내합니다.

```bash
env -u AI_API_KEY -u CODYSSEY_API_KEY python main.py commit
```

```
[ERROR] AI_API_KEY 환경변수가 설정되지 않았습니다.
       예) export AI_API_KEY="sk-cody-live-YOUR_KEY"
       키 발급: https://usr.codyssey.kr/public-api-console
```

**Git 수집을 시작하기 전에** 검사합니다(`run()`의 첫 줄이 `load_api_key()`).
다 모아놓고 "키가 없다"고 하면 사용자 시간을 낭비시키기 때문입니다.

## 1-4. Git 변경 사항이 없는 상태에서 실행하면 "변경 사항이 없습니다"에 준하는 메시지가 출력되는가?

> **한 줄 답** — 메시지를 출력하고 **API를 호출하지 않은 채** 종료 코드 **0**으로 끝납니다.

```bash
python main.py commit          # 커밋할 것이 없는 상태에서
```

```
[INFO] 변경 사항이 없습니다. 생성하지 않고 종료합니다.
```

**exit code가 1이 아니라 0인 이유**: 사용자가 잘못한 게 없으므로 오류가 아닙니다.
스크립트에서 이 도구를 호출할 때 "변경 없음"이 실패로 잡히면 파이프라인이 깨집니다.

## 1-5. 출력된 PR 본문에 Why/What/How to Test 구조가 포함되고, 각 섹션에 최소 1개 불릿이 포함되는가?

> **한 줄 답** — 프롬프트로 요청하고 `formatter.validate_pr()`이 코드로 검증합니다. 검증 실패 시 재생성하고, 그래도 안 되면 스텁을 넣고 경고합니다.

검증 항목 세 가지:
1. `## Why` / `## What` / `## How to Test` 헤더 존재
2. 각 섹션에 `- `로 시작하는 불릿 1개 이상
3. 없으면 **구조적 실패**로 판정 → 재생성 트리거

헤더는 `_find_section()`이 느슨하게 찾으므로 `## Why (변경 배경)` 같은 변형도 인식합니다.
**섹션 헤더만은 영어가 강제**(기능요구 4번 명시)라 프롬프트에 "이 헤더는 번역하지 말라"고 따로 적었습니다.

## 1-6. `-temperature` 또는 `-max-tokens` 값을 변경해 실행했을 때 출력 길이/디테일 차이가 재현되는가?

> **한 줄 답** — `temperature 0.0`은 두 번 돌려도 완전히 같고, `1.0`은 불릿 5→8개·출력 200→283토큰으로 달라집니다.

```bash
python main.py commit --temperature 0.0    # A
python main.py commit --temperature 0.0    # B — A와 완전히 동일
python main.py commit --temperature 1.0    # C — 달라짐
```

| 실행 | temperature | 출력 토큰 | 불릿 수 |
|---|---|---|---|
| A | 0.0 | 200 | 5 |
| B | 0.0 | **200** | **5** |
| C | 1.0 | 283 | 8 |

`max_tokens`도 마찬가지로 재현됩니다.

```bash
python main.py pr --max-tokens 200    # 잘림 → 재생성 → 스텁, 호출 2회
python main.py pr                      # 정상, 호출 1회
```

> ⚠️ **시연할 때 주의** — 위 수치는 2,343줄 diff에서 측정한 것입니다.
> **변경이 작으면 temperature를 올려도 결과가 거의 같습니다.** 요약할 방법이 몇 가지 없기
> 때문입니다(18줄 diff에서는 56 대 59토큰으로 사실상 동일했습니다).
> `--max-tokens`도 도구가 알려주는 `출력 N 토큰`보다 **낮게** 잡아야 절단이 보입니다.
>
> 명세는 “temperature **또는** max-tokens”이므로, 확실한 재현을 원하면
> `--max-tokens 30`으로 절단·재생성 경로를 보여주는 쪽이 안전합니다.

전체 출력은 [`verification.md` §5·§6](verification.md) 참조.

## 1-7. 커밋/PR 출력이 정의된 길이/형식 규칙을 만족하는가?

> **한 줄 답** — 프롬프트로 요청하고 `formatter.py`가 코드로 강제합니다. 위반은 `[WARN]`으로 사용자에게 알립니다.

| 규칙 | 값 | 상수 |
|---|---|---|
| 커밋 제목 권장 | 50자 | `COMMIT_TITLE_SOFT` |
| 커밋 제목 최대 | 72자 | `COMMIT_TITLE_HARD` |
| PR 제목 최대 | 80자 | `PR_TITLE_MAX` |
| PR 섹션 헤더 | Why / What / How to Test 필수 | `PR_SECTIONS` |
| 각 섹션 불릿 | 최소 1개 | `_BULLET` |
| 커밋 컨벤션 접두사 | feat/fix/docs/… (WARN 수준) | `COMMIT_TYPES` |
| 출력 구획 | 구분선/헤더로 분리 | `render_block()` |

72자 초과 시 `truncate_at_word()`가 단어 경계에서 자릅니다. 한국어처럼 공백이 없으면
상한에서 그대로 자릅니다 — 경계를 못 찾을 때 통째로 자르지 않으면 `feat:`만 남고 다 날아갑니다.

# 항목 2 — 구조 설계 (4)

## 2-1. Git 변경 사항 수집 로직과 AI API 호출 로직을 왜 분리했는가?

> **한 줄 답** — 두 작업의 성질이 정반대라 실패 원인도 재시도 정책도 다르기 때문입니다.

| | `gitctx.py` (수집) | `ai_client.py` (호출) |
|---|---|---|
| 위치 | 로컬 | 원격 |
| 결과 | 결정적 | 확률적 |
| 비용 | 무료 | 유료 (토큰 차감) |
| 실패 원인 | git 미설치, 저장소 아님 | 인증·네트워크·한도 |
| 재시도 | 의미 없음 | 의미 있음 |

**분리하지 않으면 잃는 것 세 가지**

1. **실패 지점 구분 불가.** 예외가 났을 때 "git이 실패했나 API가 실패했나"를 알려줄 수 없습니다.
   실제로 이 도구는 `[ERROR] Git 저장소가 아닙니다`와 `[ERROR] AI API 오류 [HTTP 401]`로
   완전히 다른 조치를 안내합니다.
2. **단독 테스트 불가.** 지금은 API 키 없이 `gitctx.build_context()`만 검증할 수 있습니다.
   `--dry-run` 옵션이 존재할 수 있는 것도 이 분리 덕입니다.
3. **재시도 정책 혼선.** git 수집은 재시도해도 같은 결과, API는 일시적 장애일 수 있습니다.

## 2-2. 프롬프트 구성 로직과 출력 포맷팅 로직을 어떻게 분리했고, 그 이유는?

> **한 줄 답** — 프롬프트는 "부탁"이라 보장이 없고, 포맷터는 "강제"라 보장이 있습니다. 보장 수준이 다른 것을 한 곳에 두면 디버깅할 지점이 사라집니다.

| 계층 | 파일 | 성격 | 보장 |
|---|---|---|---|
| 프롬프트 | `prompts.py` | AI에게 부탁 | **없음** (확률적) |
| 검증·후처리 | `formatter.py` | 코드가 강제 | **있음** (결정적) |

`SYSTEM_COMMIT`에 "제목 50자 이내"라고 써도 100번 중 몇 번은 어깁니다. `temperature=0.0`으로
낮춰도 0이 되지 않습니다. 반면 `truncate_at_word(title, 72)`는 100% 보장입니다.

**분리하지 않으면**: "왜 가끔 72자를 넘지?"를 만났을 때 프롬프트를 고칠지 후처리를 고칠지
판단할 지점 자체가 없습니다.

**두 파일 사이의 계약**: `prompts.py`가 출력 형식(`<<<TITLE>>>`, `<<<BODY>>>`, `## Why` 헤더)을
정의하고 `formatter.py`가 그 형식을 파싱합니다. 한쪽만 바꾸면 깨지므로 양쪽 docstring에 명시했습니다.

> 프롬프트에도 길이 규칙을 적는 이유: 애초에 지켜져 나오면 후처리로 깎을 일이 없어
> 결과가 더 자연스럽습니다. **이중 방어이지 중복이 아닙니다.**

## 2-3. API 파라미터를 CLI 옵션으로 설계한 이유는?

> **한 줄 답** — 재현성과 실험 통제입니다. 하드코딩하면 파라미터를 바꿀 때마다 코드가 달라져서 통제 변수가 무너집니다.

- **재현성**: `--temperature 0.0`으로 고정하면 같은 diff에서 같은 결과가 나오는지 확인할 수 있습니다.
  실제로 두 번 실행해 출력 토큰까지 200으로 동일함을 확인했습니다.
- **실험 통제**: 프롬프트를 고쳐가며 품질을 개선할 때, 파라미터가 고정돼야 **프롬프트 변경의 효과만
  분리해서** 관찰할 수 있습니다. 코드를 고쳐 바꾸면 "코드가 달라져서인지 파라미터 때문인지" 모릅니다.
- **용도별 최적값이 다름**: 커밋(짧고 형식적)과 PR(길고 서술적)은 적정 `max_tokens`가 달라서
  서브커맨드별 기본값을 700 / 1200으로 각각 두고 옵션으로 덮어쓸 수 있게 했습니다.

과제 예시가 `-model` 표기라 **하이픈 1개·2개를 모두** 받습니다.

## 2-4. 오류 처리를 어떤 방식으로 구현했고, 왜 그렇게 했는가?

> **한 줄 답** — 모든 오류 메시지가 "무엇이 왜 실패했고, 무엇을 하면 되는지"를 담도록 했습니다.

**예외를 계층별로 나눴습니다**

```
GitError                 (gitctx)   git 미설치, 저장소 아님
AIError                  (ai_client) API 호출 실패 — 아래를 포함
 ├─ MissingAPIKeyError               키 미설정
 └─ CallBudgetExceeded               호출 예산 초과
ValueError                          파라미터 범위 위반
```

`main()`에서 한 번에 잡되 메시지는 각자 갖습니다.

**HTTP 상태 코드를 원인별로 매핑했습니다.** 게이트웨이는 원래 API에 없던 실패 모드를 만듭니다.

| 코드 | 안내 |
|---|---|
| 401 | 키가 잘못됐거나 폐기됨 → 콘솔에서 확인 |
| 403 / 503 | **내 키는 멀쩡한데** 기관의 provider 키 미등록 → 운영자 문의 |
| 429 | 월 차감 토큰 소진 → 사용량 탭 확인 |
| 400 | 서버 응답의 `error.message`를 그대로 노출 |

403이 중요합니다 — "키를 확인하세요"가 아니라 "운영자에게 문의하세요"가 맞는 안내입니다.

**요청 전에 검증합니다.** `temperature=2.0`은 서버가 400을 주지만 그러면 네트워크 왕복을
낭비합니다. `validate_temperature()`로 미리 막습니다.

**exit code를 구분합니다.** 정상 0 / 변경 없음 0 / 오류 1 / 중단(Ctrl-C) 130.

# 항목 3 — 파라미터와 프롬프트 (4)

## 3-1. `temperature`를 높이거나 낮추면 결과가 어떻게 달라지는가?

> **한 줄 답** — 다음 토큰의 확률분포를 얼마나 평탄하게 만들지 조절합니다. 0.0은 결정적·재현 가능, 1.0은 다양하지만 형식 위반 확률이 올라갑니다.

| 값 | 동작 | 결과 |
|---|---|---|
| 0.0 | 항상 최고 확률 토큰 선택 | 결정적, 재현 가능, 보수적 |
| 0.2 (기본) | 거의 결정적 | 형식이 안정적이면서 문장은 자연스러움 |
| 1.0 | 낮은 확률 토큰도 선택 | 다양·창의적, 형식 위반 확률 증가 |

**기본값 0.2의 근거**: 커밋 메시지는 창의적인 글이 아니라 **형식이 정해진 요약**입니다.
같은 변경에 매번 다른 요약이 나오면 신뢰하기 어렵습니다.

**실측에서 관찰한 것**: `1.0`에서 불릿이 5→8개로 늘고 파일별로 잘게 나뉘었지만,
영어 프롬프트로 측정했던 회차에서는 **제목이 세 번 모두 동일**했습니다.
temperature는 분포를 평탄하게 만들 뿐이므로 **확신이 약한 지점부터 흔들립니다.**
"올리면 다 바뀐다"가 아닙니다.

> ⚠️ **Anthropic 규격의 범위는 0.0~1.0**입니다. OpenAI(0.0~2.0)와 다르며 2.0을 보내면 400입니다.

## 3-2. `max_tokens`가 결과물에 어떤 영향을 미치며, 어떤 기준으로 값을 설정했는가?

> **한 줄 답** — 품질 조절기가 아니라 **절단기**입니다. 줄이면 짧게 쓰는 게 아니라 쓰다가 중간에 잘립니다.

**가장 위험한 점: 잘려도 HTTP 200으로 돌아옵니다.** 에러가 아니라 정상 응답이고,
`stop_reason: "max_tokens"`를 봐야만 알 수 있습니다.

```python
@property
def was_truncated(self) -> bool:
    return self.stop_reason == "max_tokens"
```

PR 본문에서 이게 일어나면 마지막 `## How to Test` 섹션이 통째로 사라진 채 "성공"으로 처리됩니다.
실제로 `--max-tokens 200`으로 재현했습니다.

**값을 정한 기준**

| 명령 | 기본값 | 근거 |
|---|---|---|
| `commit` | 700 | 제목 1줄 + 불릿 3~5개 = 200~300 토큰. 여유 2배 |
| `pr` | 1200 | 3섹션 × 불릿 2~4개 = 500~700 토큰. 여유 2배 |

**"짧게 써라"는 프롬프트로 지시하고, `max_tokens`는 사고 방지용 상한으로 넉넉히 잡는 것**이 정석입니다.
길이 통제를 `max_tokens`로 하면 문장이 중간에 끊깁니다.

## 3-3. 커밋/PR 용도에 맞는 결과를 얻기 위해 프롬프트에 어떤 정보를 포함했고, 왜 그렇게 구성했는가?

> **한 줄 답** — 모델이 diff만 봐서는 **알 수 없는 맥락**만 명시적으로 넣었습니다. `요약 → 상세` 순서로 쌓습니다.

| 넣은 것 | 이유 |
|---|---|
| 현재 브랜치 | PR 초안에 필요. 브랜치명 자체가 의도를 담고 있음 |
| 변경 규모 (파일 수, +/- 줄) | 규모에 맞는 서술 톤을 잡게 함 |
| **변경된 파일 목록** | diff보다 **먼저** 배치 — 전체 그림을 준 뒤 헌크를 읽게 하면 맥락을 갖고 읽음 |
| 최초 커밋 여부 | 없으면 존재하지 않는 이전 상태와의 비교를 지어냄(환각) |
| 마스킹·절단 사실 | 모르면 `[MASKED_API_KEY]`라는 자리표시자를 변경 내용으로 서술함 |
| sanitize된 diff | 실제 재료. ` ```diff ` 펜스로 감싸 경계를 명확히 함 |
| 출력 형식 지시 | `formatter`가 파싱할 계약 |

**diff에서 읽어낼 수 있는 것은 넣지 않습니다** — 토큰만 쓰고 정보는 중복입니다.

**언어를 명시한 이유**: 지시하지 않았을 때 실제로 커밋은 영어, PR 본문은 한국어로 갈렸습니다.
**명시하지 않은 것은 "알아서 잘"이 아니라 "매번 다르게"가 됩니다.** 명세는 언어를 규정하지
않지만(`evLang: null`) 결과 예시가 전부 한국어 + `feat:` 접두사라 그에 맞췄습니다.

## 3-4. 길이/형식 규칙을 "재생성"과 "후처리" 중 무엇으로 해결했는가?

> **한 줄 답** — 둘 다 씁니다. **위반을 두 종류로 나눠** 각각에 맞는 방법을 쓰는 하이브리드입니다.

| 유형 | 예 | 성질 | 해결 |
|---|---|---|---|
| **양적 위반** | 제목 80자, 마크다운 펜스, 따옴표 | 정답이 **유일하게 결정됨** | **후처리** |
| **구조적 위반** | `## How to Test` 섹션 자체가 없음 | **정보 부족** | **재생성** |

```python
issues = validate(result)
if not issues:
    return result
if has_structural_failure(issues):
    result = client.complete(..., retry_hint)   # 2회차
return postprocess(result)                      # 나머지는 코드로 절단
```

**왜 전부 후처리가 아닌가**: 없는 섹션에 헤더는 만들 수 있지만 **내용이 없습니다.**
빈 스텁이 들어갈 뿐입니다. 형식 문제가 아니라 정보 부족이라 코드로 만들 수 없습니다.

**왜 전부 재생성이 아닌가**: 제목이 80자인 건 자르면 정답입니다. 재생성하면 토큰을 또 쓰고
결과는 같거나 더 나쁩니다. 게다가 재생성은 **성공 보장이 없습니다** — 두 번째도 어길 수 있습니다.

**재시도 예산**: 최대 1회(총 2회 상한, `MAX_CALLS_PER_RUN = 2`). 과제 제약 "1회 실행 시
호출 1~2회"가 곧 이 예산의 근거입니다. 확률적 시스템에서 재시도는 **반드시 상한과, 상한
도달 시의 결정적 fallback이 함께** 설계돼야 합니다. 그래서 재생성에 실패하면 후처리로
착지하고 `[WARN]`으로 무엇이 비었는지 알립니다.

# 항목 4 — 운영 관점 (3)

## 4-1. AI가 생성한 커밋/PR 텍스트를 바로 사용하지 않고 검토가 필요한 이유는?

> **한 줄 답** — 형식은 완벽한데 내용이 틀릴 수 있고, 그건 형식 검증으로 절대 못 잡습니다.

**이 프로젝트에서 실제로 발생한 사례**가 있습니다. PR 본문에서 AI가 이렇게 썼습니다.

```
- `gitctx.py`: Git status/diff 수집 및 마스킹 처리      ← 마스킹은 sanitizer.py의 역할
```

diff만 봐서는 두 모듈이 어떻게 나뉘는지 정확히 알 수 없어 그럴듯하게 합쳐버린 것입니다.
`formatter`는 섹션 구조와 길이만 보지 **내용의 진위는 모릅니다.**

**그 외의 이유**

1. **변경 이유는 diff에 없습니다.** 코드는 "무엇을 바꿨는지"만 담고 "왜"는 개발자 머릿속에
   있습니다. AI가 쓰는 `## Why`는 본질적으로 **추측**입니다.
2. **safe-mode 절단으로 일부만 보고 판단했을 수 있습니다.** 200줄 상한을 넘긴 변경은
   AI가 못 본 부분이 있습니다.
3. **커밋 메시지는 영구 기록입니다.** `git log`·`git blame`·릴리스 노트의 근거가 됩니다.
4. **팀 컨벤션은 코드 밖에 있습니다.** 티켓 번호 규칙 등은 diff에 없어 AI가 알 수 없습니다.
5. **책임 소재**: 커밋과 PR은 작성자 이름으로 남습니다. 검토 없이 올리면 AI가 아니라 작성자가 책임집니다.

그래서 이 도구는 **초안 출력까지만** 하고 `git commit`을 실행하지 않으며,
매 실행 끝에 검토 안내를 출력합니다.

## 4-2. `git diff`에 민감정보가 포함될 수 있는 상황과 방지 방안은?

> **한 줄 답** — 프롬프트 조립 직전 **단일 관문**을 두고 마스킹 13종 + 전송량 제한을 함께 겁니다.

**포함될 수 있는 상황**

- `.env`, `config.json` 등 설정 파일을 실수로 추적 중일 때
- 디버깅하다 코드에 키를 임시로 하드코딩했을 때
- 테스트 픽스처·시드 데이터에 실제 이메일·전화번호가 있을 때
- 주석에 내부 서버 주소·계정 정보를 적어둔 경우

**방지 방안**

| 계층 | 방법 |
|---|---|
| 마스킹 | 13종 정규식 — API 키·토큰·개인키·주민번호·카드·휴대폰·이메일 |
| 전송량 제한 | 최대 10파일 / 200줄 — 노출면과 비용을 함께 축소 |
| 단일 관문 | 상위 계층은 원본 diff를 만지지 않고 `sanitize()` 결과만 사용 |
| 투명성 | 무엇을 가렸는지 `[INFO]`로 사용자에게, 그리고 **AI에게도** 알림 |
| 사전 차단 | `.gitignore`에 `.env` 선반영 + `.env.example`만 커밋 |

**관문이 하나여야 하는 이유**: 마스킹 함수가 여럿이면 "어떤 경로로도 원본이 새지 않는다"를
**반증할 수 없습니다.** 보안 코드는 우회 경로가 0개임을 코드 구조로 보여야 합니다.

**규칙 설계에서 어려운 건 "무엇을 잡느냐"가 아니라 "무엇을 안 잡느냐"입니다.** 오탐을 가르는 세 구분선:

| 구분선 | 가르는 것 |
|---|---|
| 값에 **따옴표 필수** | `PASSWORD = "hunter2"`(비밀) vs `password = user.password`(코드) |
| 값 **8자 이상** | `TOKEN_TYPE = "Bearer"`(6자) 제외 |
| `.env` 규칙은 **`=` 앞뒤 공백 금지** | `.env`는 `KEY=value`, 파이썬은 `key = value` |

세 번째를 안 걸면 `access_token = response.json()["access_token"]` 같은 평범한 코드가
마스킹되어 diff를 읽을 수 없게 됩니다. 14개 케이스로 검증했습니다([`verification.md` §8](verification.md)).

**한계도 인정해야 합니다.** 정규식은 **형식이 있는 것만** 잡습니다. 내부 서버 주소, 사람 이름,
사업 로직 같은 비정형 비밀은 못 잡습니다. 마스킹은 최후 방어선이 아니라 **안전망**이며,
근본 대책은 애초에 비밀을 커밋하지 않는 것입니다.

## 4-3. 실제 팀 프로젝트에 적용한다면 무엇을 가장 먼저 추가/개선하고 싶은가?

> **한 줄 답** — 우선순위 기준을 "**없으면 도구를 못 쓰게 되는 것 → 있으면 훨씬 좋아지는 것**" 순으로 잡았습니다.

**1순위 — 팀 컨벤션 설정 파일 (`.ai-gitgen.yml`)**

팀마다 커밋 규칙이 다릅니다(prefix, 스코프, 티켓 번호, 언어). 지금은 컨벤션을 바꾸려면
`prompts.py`를 고쳐야 하는데, 그러면 팀원마다 코드가 갈라집니다. 설정을 저장소에 커밋하면
**팀 전체가 같은 규칙**을 쓰고 코드는 공유됩니다.
→ *도구가 개인용에서 팀용이 되려면 반드시 필요*

**2순위 — 브랜치명·이슈 트래커 연동**

`## Why`가 지금은 AI의 추측입니다(4-1 참조). 브랜치명(`feature/PROJ-123-...`)에서 티켓을 뽑아
제목/설명을 프롬프트에 넣으면 **추측이 사실로 바뀝니다.**
→ *결과물 품질에 가장 큰 영향*

**3순위 — 대형 변경 대응 (diff 요약 압축)**

현재는 200줄에서 자릅니다. 큰 PR에서는 잘린 부분이 핵심일 수 있습니다. 파일별 1차 요약 후
종합하면 전체를 보면서도 토큰을 아낄 수 있습니다.
→ *다만 API 호출이 늘어 비용 제약과 충돌하므로 3순위*

**4순위 — `--apply` 옵션 (git commit 실행)**

편하지만 지금도 복사-붙여넣기로 가능하고, 검토 없이 커밋하는 습관을 만들 위험이 있습니다.
→ *편의는 크지만 리스크가 있어 후순위*
